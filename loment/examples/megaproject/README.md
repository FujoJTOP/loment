# `megaproject` —— 100 个 Python 语法模块、1000 个函数的超大型项目

**用 Python 的拼法写的 Loment**，规模拉到"超大型"这一档：**100 个模块 × 10 个函数 = 1000 个
函数**，由**原生 Loment** 宿主一次 `use` 全部模块、一次编、一次跑。

判据在 `tools/loment_megaproject_test.py`。

```
megaproject/
    README.md      这一份
    main.lomt      宿主 —— **原生 Loment**，use 全部 100 个模块，把每个 entry() 折成一个数
    m000.lomt …    100 个计算模块 —— **Python 拼法**（首行 `choose write grammar python`）
    m099.lomt
```

每个模块 **恰好 10 个函数**（`f0`…`f8` 加一个 `entry`，合计 100 × 10 = **1000**），
形状固定但常数各不相同：`f0` 循环求和、`f1` 跨函数调用 + 整除、`f2` 移位异或掩码、
`f3` elif 链、`f4` 递归、`f5` 嵌套 `for`、`f6` 8 轮 LFSR 移位、`f7` 格雷码解码、
`f8` 双 `if` 收敛、`entry` 把前八个折起来取模 251。

## 三条约束，都是实测逼出来的

1. **函数名必须全局唯一（`m007_f3` 这种）。** 单元的**发射符号是平的**（ABI）：两个模块
   各写一个 `f0` 会被拒。这不是本语料的偏好，是语言的规则 —— 报出来的那条消息本身也指错了
   东西（[#221](https://github.com/FujoJTOP/loment/issues/221)）。

2. **一个模块级常量都不用。** 函数内与模块常量同名的局部会被**静默忽略**
   （[#216](https://github.com/FujoJTOP/loment/issues/216)），参数与常量同名会被误报成
   "参数重复"（[#217](https://github.com/FujoJTOP/loment/issues/217)）。该当常量的三个数
   直接写成字面量 —— 避开的是**缺陷**，不是语义差。

3. **语料是生成物，判据钉住它不漂。** 100 份手抄必然漂，所以
   `tools/loment_megaproject_test.py` 里有一份 `gen_module()`；仓里这 100 份必须**逐字节**
   等于它的产物。与自举种子同一条纪律（`loment_seed_test`：**能藏的前提是它可复现**）。

## 三方（三个数必须相等）

| | 值 | 怎么来的 |
|---|---|---|
| control（真 CPython） | **206** | `gen_module()` 那些函数体的**直译**（同源，不是独立推导） |
| loment（前门 → lomelf → WSL） | **206** | 100 个 `.lomt` 走前门翻译 → `lomentc` 检查 → LLVM IR → `lomelf` → WSL 跑 |
| expected（独立推的） | **206** | 上面那张表 + `oracle_total()`（**另写一遍**：闭式、位串、`max`） |

```
python tools/loment_megaproject_test.py
#   101 份文件与生成器逐字节一致（100 模块 + 宿主）
#   100 个模块、1000 个函数、宿主 use 100 个模块
#   1000 个函数 / 100 个模块 -> loment=206 cpython=206 expected=206
```

## 天花板在**形状**上，不在数字上：一个文件最多 `use` 300 条

要顶到**上千个模块**，先撞到的不是编译器的力气，是**一条语言规则**：

```
$ （一个宿主平铺 301 条 use）
lomc.LomError: 1:1: 模块 main 的 use 有 301 条, 超过上限 300 —— 门面拆小, 别把整库塞进一个文件
```

（`docs/143` §93；判据 `test_a_host_cannot_use_more_than_the_cap_of_modules` 钉着它。）

所以"1000 个模块"**不可能**由一个宿主平铺 `use` 完 —— 必须**分层**：叶子是 Python 拼法的
模块（子集里没有 `use`，只能被用），中间是**原生** hub，每个 hub `use` 一批叶子并把它们
折起来（`hub_entry()`），宿主再折 hub。`gen_tiered(hubs, leaves)` 就是这个形状。

```rust
module hub003                     // 原生 Loment
use "m0300.lomt"                  // …一直数到第 400 个叶子（100 条 use）
pub fn hub003_entry() -> i64 {
    let acc: i64 = 0;
    acc = (acc * 31 + m0300_entry() as i64) % 1000003;
    // …
    return acc;
}
```

## 实测：顶到 **1011 个模块**

本机、仓内 HEAD（`--scale HUBSxLEAVES` 就是量这张表的）：

| 规模 | 模块数 | 生成 | load+check | IR | lomelf | 汇编产物 | 结果 |
|---|---|---|---|---|---|---|---|
| 3 hub × 100 叶子 | 304 | — | 19.4s | 2.0s | 0.9s | 1.4 MB | ok |
| **10 hub × 100 叶子** | **1011** | 1.2s | **192.1s** | 7.0s | 2.8s | **4.73 MB** | ok，rc=87 = 独立算的 |

另外（单文件形状，见 `loment_megaproject_test.py` 的头注）：

| 规模 | 结果 |
|---|---|
| 1 模块 × 1000 函数 | ok，检查 6.8s |
| 单函数 2000 条语句 | ok |
| 单模块 500 个常量 / 300 分支的 elif / 200 层括号 | ok |

**这一档没有崩，但代价是实的**：load+check 在 300 模块（19s）到 1011 模块（192s）之间
是**明显超线性**的（3.3 倍模块、9.9 倍时间）。到上千模块时，瓶颈已经是**前端**（前门翻译 +
检查），不是后端（IR 7s、lomelf 2.8s）。要真拿它当日常路径，值得先量清楚那个超线性项在哪儿。

`use` 那一档的上限与外层数量无关：hub 的 100 条、宿主的 10 条，都远在 300 以下。
