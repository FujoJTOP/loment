# 212 · Loment 的逃生舱：外包给谁

> 状态: **研究稿**（2026-10-09）。起点是一次测量，不是一次设计。
> 2026-10-09 量到：数组基准上 Loment（`lomelf` 原生产物）比 C -O2 **慢 10.7×**。
> 本文问的**不是**"怎么把 `lomelf` 写快点"（那是 `docs/167` 那条线），
> 而是 **Python 那个逃生舱，在 Loment 里的对应物是什么**。
> 结论先行：**外包给 LLVM**；落地形态 = `extern fn` + `--link` 链一个**预优化过的 `.o`**，
> 那个 `.o` 由 **lompi** 内容寻址地分发。**三件套里两件已经在了**（FFI stage 1、lompi）。
> 每条主张都挂在**可证伪的判据**上（§7），不靠形容词。

## 0. 一句话

> **Python 慢，是因为热点外包给了"别人在别处编好的机器码"。Loment 没有这个舱 —— 它自己就是那个别人。**
> 本文说：这个舱**存在**，而且**已经在造了**。它叫 **`extern fn` + `--link` + lompi**；
> 外包的对象不是一门语言，是**同一个优化器（LLVM）**，只是**在另一个时间点、另一台机器上**跑。

## 1. 起点：那 10.7×（测量，2026-10-09）

三条基准，每语言同一份算法、同一 `n ≈ 1e8`。C 与 Loment 在 **WSL 同一 OS**（`gcc` / `lomelf`），
Rust/Java/CPython 在 Windows。单位 ms，"min of 3"。

| 基准 | C -O2 | C -O0 | **Loment** | Rust -O | Java 23 | CPython |
|---|---|---|---|---|---|---|
| ALU · 4 条独立链 | 85 | 99 | **99** | 107 | 262 | 34 295 |
| 调用密集 · 每圈一次调用 | 93 | — | **375** | —\* | 264 | 11 055 |
| **数组 · 逐元素读写** | **32** | 90 | **342** | **33** | 231 | 12 431 |

\* Rust 把那条 LCG **闭合求解**了（循环消失），该数无效 —— 这也是"同一后端"的一个旁证。
三份基准的结果值跨语言**逐位相同**（数组那条 `2197884412188410368`，Loment 退出码 `%256` 相符）。

**读法**（三条一起看才成立）：

* **ALU 那条**：Loment ≈ C -O0，只比 -O2 慢 16%。因为它是**延迟受限**（串行乘链）——
  栈机多出来的访存**走空闲端口、躲在链的延迟阴影里**，几乎免费。这条**看不见** Loment 的亏。
* **调用密集**：Loment = C -O2 的 **4×**。瓶颈从"依赖链"换成"**调用开销**"（参数走栈 + 无内联），
  栈机的亏**无处可躲**，露一半。
* **数组**：Loment = C -O2 的 **10.7×**，连 **C -O0 都慢 3.8×**，甚至比 JVM 慢 1.5×。
  有 ILP + 访存 ⇒ **亏全露**。

**10.7× 拆成两段**：

* **Loment 342 vs C -O0 90 = 3.8×** —— 连"没优化的 C"都不如。来源：`lomelf` 是**栈机**
  （`tools/lomelf.py:18`："每个 SSA 值一个栈槽……**不做寄存器分配**"）+ 冗余 IR
  （一次 `a[i] = a[i]*3+i+k` 里那个 `i` 被**读了 3 次**）。gcc 就算 `-O0`，局部也还在寄存器里。
* **C -O0 90 vs C -O2 32 = 2.8×** —— 少了 LLVM 的优化：`mem2reg`（治满屏 `alloca`）+ **向量化**
  （AVX2 一次 4 个 u64）。

**根因一句话**：**Loment 的产物链里没有优化器。**
- 包内 `build`/`run` 的链接器是自举的 `lomelf`（`tools/loment_dist.py:57`："有它之后 **包里不再需要 clang**"）；
- `lomelf` 是**正确优先的栈机**，不做任何 pass（`tools/lomelf.py:18`）；
- 全链**没有一处 `-O2`** —— 只有 `tools/loment.py:241` 的 `-O1`（开发用 bench）、
  `tools/loment.py:289` 的 `-O0`（cov），连 IR 头上建议的那句也是 `clang -O1`
  （`tools/lomentc.py:6132`）。

**同一条账**也解释了门禁：自举编译器**本身**就是这个栈机产物 —— 编一个 ~200 KB 的
`codegen.lomt` 要 **5.9 s**，而门禁把它重复几十上百次。

## 2. Python 的逃生舱 = 三件套（结构）

"Python 慢却能用"这件事，拆开是**三样东西**，缺一不成立：

| # | 要什么 | Python 的对应物 |
|---|---|---|
| 1 | **一门带优化器的第二语言** | C（`numpy`/`PyTorch` 的内核是 C/C++/Fortran） |
| 2 | **一条稳定的 ABI 边界** | C ABI / CPython C-API |
| 3 | **一个预编译内核的仓** | **PyPI 上的 C wheel** |

**第 3 条最常被忽略、却最关键**：Python 快，**不是因为"能调 C"**，是因为 **`numpy` 早在别处被编好了**。
没有 PyPI 上那些 wheel，"能调 C"也**没东西可调**。所以"逃生舱"这个词，落点其实是**一个仓**。

## 3. Loment 的三件套：两件已到，缺一件

| # | 要什么 | Loment 的对应物 | 状态 |
|---|---|---|---|
| 1 | 带优化器的后端 | **LLVM**（见 §4） | 有，但**没接** |
| 2 | ABI 边界 | **`extern fn` + `--link OBJ`**（`docs/173`） | ✅ **stage 1 已发货**（`0.1.4-pre2`） |
| 3 | 预编译内核的仓 | **lompi**（库=目录，**身份=内容哈希**，`lompi/lpi_cli.lomt:475`） | ✅ **已有** |

**`extern fn` 那条不是纸面的**：`docs/173` §2 记着 stage 1 已经能
"读一个外部 ELF64 可重定位目标文件（`.o`），与 Loment 自己的产物合并、解析符号、应用重定位
（`R_X86_64_PC32`/`PLT32`/`64`/`32S`）"，判据是"一个 `.c` 编成 `.o`，Loment 调它，`lomelf` 单独链接，
跑出正确答案"（`tools/loment_elf_test.py` 里那条 FFI 判据，连自举镜像都钉了）。
CLI 面：`tools/lomcli.lomt:695` —— *"`--link OBJ` adds a foreign ELF object (FFI): give the `.o`
you compiled yourself."*

⇒ **"外包给谁"的答案是：那个 `.o`。** 它可以是**任何 C-ABI 编译器**产的机器码 ——
`clang -O2` / `gcc -O2` / `rustc --emit=obj`（`#[no_mangle] extern "C"`）……
`docs/173` §2 那张表把这些语言一次性收进"C ABI 一族"。

**所以缺的只有一件事**：把"预优化过的 `.o`"**放进 lompi、按内容寻址分发**的那套配方。
`lompi` 已经是"库=目录、身份=内容哈希"，它**天生**就是个 wheel 仓 —— 只是里面今天装的是 `.lomt` 源码，
不是 `.o`。

## 4. 为什么"理论上绝对存在"：Loment 的 IR 就是 LLVM IR

这条不是愿望，是**已经被量出来的**：

* **Rust 33 ms ≈ C 32 ms**（§1 数组那条）—— 同一个后端（LLVM），**天花板就是 C**。
* **Loment 发的是标准文本 LLVM IR**：`tools/lomelf.py:20` —— *"**只吃文本 IR**：不依赖编译器内部结构，
  任何产出同一子集 `.ll` 的东西都能喂进来。"* 而 `clang` 吃的**正是同一种文本 IR**。
* 于是"把 Loment 的函数喂给 LLVM `-O2`"不需要任何新机制 —— **它今天就能跑**，
  缺的只是**把它接进 `build` 这条链**。

**这正是 Loment 比 Python 强的地方**：Python 的热点必须用**另一门语言**（C）重写；
Loment **不必** —— 内核照旧用 Loment 写，只是**离线优化过一次**。**一门语言，两个时间点。**

> ⚠ **一处真卡点（`docs/173` 的活，不是本文的）**：`lomelf` **自己**的调用约定**不是 C ABI**
> （`tools/lomelf.py:17`："实参一律走**栈**……**不保证 System V / C ABI**"）。所以"喂给 clang"
> 与"链进 lomelf 产物"是**两件不同的事**：前者产的是 C ABI 函数，后者要 `extern fn` 那座桥。
> `docs/173` stage 1 把桥修好了 —— 本文只是**用**它，不重造它。

## 5. 落地形态：两种粒度（从粗到细）

**粒度 A —— 整程序 opt-in**（最简）：

```
loment build --opt prog.lomt     # 有 LLVM 就走 clang -O2，没有就退回 lomelf
```

* 好处：一行的事，把 §1 那 10.7× **全收回来**（`clang -O2 prog.ll` 直接吃 Loment 的 IR）；
* 代价：**构建机要有个 LLVM**。这与"从种子起头、**不依赖任何外部工具链**"（`docs/173` 头部）
  那条线**直接冲突** —— 所以它必须是**可选**的，不能是默认。

**粒度 B —— 热点内核 `--link`**（numpy 的形态）：

1. 热点函数在**有 LLVM 的机器上**编成 `.o`（`clang -O2`，freestanding、自足 ——
   这正是 `--link` 的既有要求：*"self-contained, no relocations, no undefined symbols"*）；
2. 那个 `.o` 的**字节进 lompi**（内容寻址 ⇒ 可复现、可去重、可缓存）；
3. 端机 `--link` 进来 —— **不需要 clang，只要那个 `.o` 的字节**。

粒度 B 才是"**舱**"：它把优化**挪到别处、挪到别的机器、挪到别的时间**，
而端机拿到的仍然是一份**可复现的字节**。这与 PyPI wheel **是同一个形状**。

### 5.1 无 libc 就得自己提供那三个名字（2026-10-10 实测）

粒度 A 真的接到打包链上之后，8 个入口里只有 4 个走成了 clang —— 另外 4 个不是"IR 非法"，
而是**链接期**：

```
loment-lomelf / loment-cli :  undefined symbol: memset
loment-driver (种子)       :  undefined symbol: memmove
lompi                      :  （另一回事：IR 合法性，见 §8 的跟进行）
```

原因不在我们的代码，在优化器**太聪明**：`-O2` 认得"按字节铺/搬"的循环，会把它改写成对
`memset` / `memcpy` / `memmove` 的调用 —— 它既认得出 **Loment 运行期里那两段循环**，
也认得出**用户代码**里同样的循环。而 Loment 是 freestanding、没有 libc，于是那几个名字
没人定义。**这不是 `--opt` 的毛病，是任何"把 IR 交给真优化器"的方案都会撞上的一堵墙**：
一个 freestanding 运行期的本分，就是把优化器敢合成的名字都备一份。

补在哪里，有三条路，各自都试过或想过：

| 补在哪 | 代价 |
|---|---|
| **链接这一步**（选定） | `loment_dist.py` 一个常量 + 启动器一段 heredoc；**前端一行不动** |
| IR 运行期里（改名成标准名） | 要改**两个实现** + 重出种子 + 重出**提交进仓库的 genesis 二进制** + 两份 SHA256SUMS |
| 编进粒度 B 的那个 `.o` | 与"端机不需要编译器"的立意冲突，而且两边都补会**重复定义** |

三条都是"公开定义"（`internal` 满足不了 LLVM 合成到**外部**名字上的调用，实测仍然
`undefined symbol`）。选第一条的判据很直白：那条路的产物**根本不经过 `lomelf`**，
所以运行期里那三行对它是零收益，而改前端的代价是重建整条自举链。

补过之后：`[--opt] clang -O2 了 7/8 个入口` —— 只剩 `lompi`，它卡在 §8 记的那条 IR
合法性跟进行上（自举侧把大整型字面量发成 `i32`），与 libcall 无关。

**判据**（`loment_dist_test`）：光"`--opt` 编得动 `user_hello`"是不够的 —— 那个程序里
没有字节循环，看不见这一格。所以另起了 `OPT_LIBCALL_PROBE`：一段**同时有铺与搬**的
程序，`--opt` 必须链得起来，且跑出来结果正确。少补任何一个符号这条就红（实测：
不补时 clang 报 `undefined symbol: memset`）。

### 5.2 **`--opt` 现在还递不出去**：它会把这个编译器编坏（2026-10-10 实测）

链接补齐之后 `--opt` 能编的东西变多了 —— 然后就撞上了这条**比慢严重得多**的事实：

| 同一份驱动 IR | 结果 |
|---|---|
| clang **-O0** | 正常（`rc=0`，编得动） |
| clang **-O1** | **SIGSEGV**（`rc=139`，一跑就崩） |
| clang **-O2** | **SIGSEGV** |

**不是补的那三个 libcall 的错。** 把 `memset`/`memcpy`/`memmove` 换成 LLVM 自己的
`llvm.memset` / `llvm.memcpy` / `llvm.memmove` **内建**（语义由 LLVM 保证）再编一次
`-O1`，**同样段错误**。所以问题在**驱动那份 IR 本身**：有 `-O1` 会踩到的东西 ——
UB，或某个 LLVM 的假设（对齐、未初始化读、指针 provenance），或者两者都有。

**有多宽**：`lomelf` 与 `lomcli` 用 `-O2` 编出来，跑 `help` 与 `-O0` 产物**逐字节同输出**，
而且 `lomelf -O2` 汇编 992 KB 的 IR 与 `-O0` 产物**逐字节相同** —— 所以不是"整条链都被编坏"。
目前**确认坏的就是驱动**（入口里最大的一份，而且只有它是**从种子**来的，不是 stage1 现编）。

**所以现在这么办**：`tools/loment_dist.py` 里有一张 `NO_OPT_TOOL`，**驱动这一格点名退回
lomelf** —— 慢，但是对的。把一份一跑就崩的编译器递出去，比给它一份慢的糟糕得多；
"递出去的东西必须可信"这一条优先于快。修好这一条之后把那格删掉，驱动才配吃 `--opt`。

**顺带一个数**：lomelf 编出来的驱动，**编它自己**要 **5 分 28 秒**（WSL，3.2 MB IR，
单线程）。门禁慢的那个根因就在这里 —— 而 `--opt` 那条路现在**还接不上**（见上）。
也就是说 §1 那 10.7× 的账，到今天为止**一分钱都还没收回来**：能收的那个后端（clang）
在这份最大的入口上会编坏，先得把 §5.2 查清楚。

## 6. 真正的代价：可复现（Loment 独有，Python 从不付）

Python **从没承诺** hermetic build；Loment **承诺了**（种子自举 + `loment_seed_test` 的逐字节判据）。
所以原样"shell 到 clang"会破两条，**每条都有解法，但每条都要认账**：

1. **LLVM 版本不同 ⇒ 产物不同** ⇒ "两个实现逐字节相同"那族判据碎。
   解法：**钉死 LLVM 版本 + 把产物哈希进 lompi**。你分发的是**字节**，不是依赖 ——
   复现性因此**保住**（哈希钉住的那个字节，永远是那个字节）。
2. **构建机必须有一个 LLVM** ⇒ "从种子起头、无 clang"那条线破。
   解法：降级成**可选** —— 像 `numpy` 之于 CPython：**基线是解释器，加速件按需装**。
   **纯 Loment 程序仍然 freestanding**（`docs/173` §0 的原话）；**只有用了加速件**的才带那个依赖。

> **一句话：这道舱门的价钱是"可复现 vs 优化" —— 而 lompi 的内容哈希正是同时付两样钱的那张票。**

## 7. 另一条路：不外包（`lomelf` 自己长大）

若连外部 LLVM 都不想要，那就**把优化器写进 `lomelf`**（那是 `docs/167` 那条线的工作）：

| 加什么 | 治 §1 的哪一段 | 难度 |
|---|---|---|
| `mem2reg`（消 `alloca`/冗余 load） | 3.8× 的**大半** | 中 |
| **寄存器分配** | 3.8× 的**剩下一半** | **高**（真正的后端工作） |
| 简单**向量化** | 2.8× 的大头 | 中 |

理论上这条能到 C -O2 的 **60–80%**。但它是**外包给未来的自己**，不是"舱"：
它把工作量全留在 Loment 这一侧，而且**每加一格都要两个实现逐字节对齐**。

## 8. 判据（每条都能证伪）

| 主张 | 判据 |
|---|---|
| **Loment 的 IR 喂得进 LLVM（天花板是 C）** | 同一份算法，`Rust -O` 与 `C -O2` 的时间**同量级**（§1 数组那条：33 vs 32 ms）；反过来说，若二者差出一个数量级，本文 §4 的前提就不成立 |
| **`--link` 能链外部 `.o`** | 已存在：`tools/loment_elf_test.py` 的 FFI 那条（`一个 .c 编成 .o，Loment 调它，lomelf 单独链接，跑出正确答案`，且自举镜像逐字节相同） |
| **lompi 能内容寻址分发** | 已存在：`lompi/lpi_cli.lomt:475`（`identity = content hash`）+ `lompi.lock` 的"名字 版本 身份" |
| **`lomelf` 是栈机（3.8× 的来源）** | `clang -O0` 与 Loment 在**同一份算法**上的时间比 —— §1 数组那条是 90 vs 342 ms；若把 `lomelf` 的寄存器分配做出来，这个比值应当塌下去 |
| **可复现能保住** | 一份预优化 `.o` 的 sha256 进 lompi，端机按哈希取 —— 与 `loment_release` 对 531 件的做法同形 |
| **门禁慢与运行慢同根** | 自举编译器编 `codegen.lomt`（~200 KB）的**绝对时间**（今天 5.9 s）；若把它换成一个 `-O2` 产物重编，时间应当塌一个量级 |

## 10. 收口

**"Loment 外包给谁"的答案是：外包给 LLVM —— 但不外包给"运行期"，外包给"另一个时间点的构建"。**

* 对象：**同一个优化器**（Rust 用它、C 用它、Loment 的 IR 也喂得进它）；
* 通道：**`extern fn` + `--link`**（已发货）；
* 仓：**lompi**（已是内容寻址，缺的只是往里放 `.o` 的配方）；
* 价钱：**可复现** —— 用 lompi 的内容哈希付。
