# 200 — `lomelf` 的零碎表：容量、越界为什么是静默的、以及台面（`docs/192` 的姊妹篇）

`docs/192` 记的是**输入缓冲**那条上限（种子 `.ll` 装不装得进 `lomelf`）。这一篇记的是
**同一个病的另外三处**：`lomelf.lomt` 里那几张"单调 bump"的小表，以及 `lomrel.lomt`
的归一化副本。2026-09-20 实测撞上，
起因是 `docs/189` S1 第十九格（自举侧的 Potato 发射）把驱动链加长了。

## 1. 症状：一条空白标签名

自举链的第 1/4 步（`genesis` 把种子汇编成 stage1）报：

```
lomelf: 未定义的标签: 
```

**冒号后面是空的。** 没有文件名、没有行号、没有"哪个标签"—— 而 `.ll` 是逐行语法，
按常理该报出一个具体的名字。同一份种子喂给**参考实现**（`tools/lomelf.py`）完全正常，
所以这是一处**两个实现不一致**，而不是种子坏了（种子与参考实现逐字符相同，
`loment_seed_test` 一直绿着）。

## 2. 定位：先把"静默"变成"响亮"

`lomelf.lomt` 里那几张表都是这样的形状：

```rust
fn gadd(tab: ptr, ...) {
    let gi: u32 = cell(tab, C_NG);
    let gbase: u32 = TB_G + gi * 32;   // ← 没有任何边界检查
    ...
    setcell(tab, C_NG, gi + 1);
}
```

表与表**首尾相接**排在同一块 2 MiB 的表区里，于是第 N+1 条写的是**下一张表的开头**。
越界几十条不会立刻崩，只会把邻居改坏 —— 报出来的错离现场很远（这里：全局表写进标签表，
查标签查出一个空名字）。

所以修法第一步不是"抬容量"，是**让越界出声**。六个 `*_add` / `*_put` 各补一条守卫，
与 `IN_CAP` 那条（`docs/192` §1）同一个形状：

```rust
if gi >= TB_G_MAX {
    let _f: u32 = fail("全局表满了 — 抬高 TB_G 的容量 (loment/tools/lomelf.lomt 的 TB_G_MAX)");
}
```

加完再跑一次 bootstrap，它当场说出了真话：

```
lomelf: 回填表满了 — 抬高 TB_FIX 的容量 (loment/tools/lomelf.lomt 的 TB_FIX_MAX)
```

**这就是"响亮"的价值**：第一次抬了全局表（1801 → 2086 条，旧上限 2048）之后，
下面还压着一张回填表，如果不加守卫，第二次仍然是空白标签名。

## 3. 两处抬高与整条表区的重排

| 表 | 旧上限 | 新上限 | 旧起址 | 新起址 |
|---|---|---|---|---|
| 全局表 `TB_G` | 2048 | **4096** | 256 | 256 |
| 标签表 `TB_LBL` | 16384 | 16384（不动） | 65792 | **131328** |
| 回填表 `TB_FIX` | 16384 | **32768** | 459008 | **524544** |
| 槽表 `TB_SLOT` | 32768 | 32768 | 917760 | 1442048 |
| alloca `TB_ALLOC` | 8192 | 8192 | 1442048 | 1966336 |
| `TB_ARG` | — | — | 1573120 | 2097408 |
| phi `TB_PHI` | 512 | 512 | 1573504 | 2097792 |
| `TB_IDATA` | — | — | 1581696 | 2105984 |
| `TB_EXT` | 4096 | 4096 | 1587200 | 2111488 |
| `TB_OBJ` | 256 | 256 | 1588000 | 2112288 |
| `TB_FREL` | 4096 | 4096 | 1589000 | 2113288 |

因为各表**首尾相接**，抬一张就是"它之后的所有起址整体后移"：全局表 +65536
（= 32 × 2048），回填表 +458752（= 28 × 16384）。表尾最后一个偏移 2244360，
所以 `M_TAB`（表区）跟着从 2 MiB 抬到 **4 MiB**，`M_OBJ`（`= M_TAB + 表区`）与
`ARENA`（`= M_OBJ + OBJ_CAP`）依次后移 —— 与 `docs/192` §2 抬输入缓冲时同一条式子。

## 4. 判据：把余量变成看得见的预算

新加 `loment_genesis_test::test_seed_fits_lomelf_table_caps`，与 `IN_CAP` 那条**同一个
形状**（从 `lomelf.lomt` 里**读**上限，不另抄一份）：它按表模型数一遍种子，断言三张表都
装得下，并把余量打出来：

```
全局表 2086 / 4096, 余量 2010
标签表 12144 / 16384, 余量 4240
回填表 15686 / 32768, 余量 17082
```

三个数的数法（判据的 docstring 里也写着）：

* **全局表** = `^@x = ` 的行数。参考实现给**每个字符串字面量站点**发一个 `.str.<函数>.<序号>`
  全局、**不按内容去重**，所以"驱动链里多几十个字符串字面量"就等于"全局表多几十条"
  —— 这正是这一格撞墙的原因（第十九格自己就带了上百条 JSON 片段字面量）。
* **标签表** = 全局 + `declare` + `define` + 基本块名（`lbl_add` 的四类调用点）。
* **回填表** = 每次 `call` / `br` 一条，**加上"每个函数里引用到的全局"各一条**（`em_mov_abs`；
  槽表按函数去重，同一个全局在一个函数里引用多次只算一次）。

这个回填模型用**旧上限验过**，所以它可信：旧上限 16384 下，HEAD 那版种子算出来 13634
（过），2026-09-20 那版算出来 15686（当场顶破）—— 与实际行为一致。

**现在最紧的是标签表（74%）**，不是刚抬过的两张。下次撞墙大概率在它。

## 5. 同一天里的**第三处**：`lomrel` 的归一化副本（2 MiB）

把上面两处修完、`loment_seed_test` 4/4 之后，`loment_rel_test` 红了，而且红得**很像"清单过期"**：

```
[DIFF] loment/build/selfhost_driver.ll
[DIFF] loment/build/genesis/lomelf-linux-x64.elf
...
loment_release: 260/486 一致
```

而两边的**写**（`--emit`）是逐字节相同的，`--checksums` 也一致 —— 只有 `--check`（读清单、
逐件重算哈希）说 226 条对不上。**根因**：`lomrel.lomt` 的 `M_NORM` 是固定的 2 MiB
（`NORM_CAP = 2097152`，通用换行归一化的副本），而清单里**有比它大的工件** —— 自举种子。
越界正好写进紧挨着的 `M_CUR`（**已装载的清单**），于是：

* 报出来的不是"这个文件的字节不对"，而是**它之后每一条都对不上**（清单被改坏了）；
* 分界点精确落在种子那一条（清单第 260 条 = 2432497 B 的种子）；
* 而"两边的写一样"是因为**写**走的是目录遍历那条路，不经过归一化副本。

修法：`NORM_CAP` 抬到 **4 MiB**（= `IN_CAP`：**读得进来的就得归一化得了**），`M_CUR` 与
`ARENA` 依次后移；`sha_of_file` 里补一条守卫（超了就报错退出，别静默写坏清单）。
判据是 `loment_rel_test::test_seed_fits_lomrel_normalization_buffer` —— 与 §4 那两条同一个
形状（从 `lomrel.lomt` 里**读**上限、报余量）：

```
最大工件 loment/build/selfhost_driver.ll 2432511 B / 归一化上限 4194304 B, 余量 1761793
```

**三处的共同形状**（这张表值得记）：都是"**一块定长的缓冲 + 一个更大的工件**"，
都是**单调写**、越界都**不报错**，而症状都离现场很远：

| 处 | 缓冲 | 越界的症状 |
|---|---|---|
| `lomelf` 输入（`docs/192`） | `IN_CAP` | 截断的 `.ll` → 汇编出一个**跑起来段错误**的可执行文件 |
| `lomelf` 三张表（本文 §3） | `TB_G` / `TB_FIX` | 写进邻居表 → `未定义的标签: `（**空名字**） |
| `lomrel` 归一化（本节） | `NORM_CAP` | 写进已装载的清单 → **从某一条起后面全对不上** |

## 6. 没做的（写明，不装作没有）

* 守卫只**报错退出**，不"自动扩容" —— 与 `IN_CAP` 那条同一个取舍：容量是编译期布局，
  运行期只能说"装不下"。
* 三张**每函数**的表（槽 / alloca / phi）也补了守卫，但它们离上限很远，没有单独的预算判据
  （数它们要按函数建模，收益不抵成本）。
* `TB_EXT` / `TB_OBJ` / `TB_FREL` 的注释里那三个容量**互相重叠**（`TB_EXT` 声明的 32768
  已经越过了 `TB_OBJ` 的起址）—— 这是本篇之前就有的口径不一致，实际用的容量更小；
  这一轮只做**整体平移**，没有顺手改它们的数（改了就得先弄清外部目标文件那条路真实用多少）。
