# 192 · lomelf 的输入上限：**越界是静默截断**，产出一个启动就崩的二进制

> 2026-09-18 写 `choose write grammar` 的自举侧守卫时撞上的（`docs/188` §7.2 末有那一段
> 的完整来龙去脉 —— 包括**我先把因认错了**那半）。这里只记**工具这一侧**的事实。

## 1. 症状

`loment_seed_test` 的三阶段定点判据红：stage1 编 `driver.lomt` 时**段错误**（退出 139）。

它不是"某段源码有问题"。决定性的一步：**把那段新代码的调用点删掉**（函数还在树里、
但**永不执行**），照样崩 —— 崩的是**汇编出来的那个二进制**，不是它跑的某条路。

## 2. 机制：`read_all` 读满就返回，没人看文件还有没有剩

`loment/tools/lomelf.lomt`（genesis 的源）：

```rust
// lomelf.lomt:3516
let n: u64 = read_all(fd as u64, inb, IN_CAP as u64);
syscall4(3, fd as u64, 0, 0);
if n == 0 {
    return fail("输入为空");
}
```

`read_all` 的循环条件就是 `off < cap` —— **读够 `cap` 就停**，它不知道文件到底多长。
于是超过 `IN_CAP`（2 MiB）的 `.ll` 被**截掉尾部**，剩下的字节照常进汇编器：
`.ll` 是**逐行**语法，截断点之后的函数定义凭空消失 —— 汇编出来的是一个**缺胳膊少腿**
的可执行文件，跑起来在 `_start` 里就段错误。

**名字池那一半是会响的**（不是这个 bug 的一部分，但同一条边界）：

```rust
// lomelf.lomt:2676 —— 外部符号名池从**输入文本的末尾**往 IN_CAP 长
fn copy_name(tab: ptr, t: ptr, p: ptr, off: u32) -> u32 {
    let cur: u32 = cell(tab, C_EXTN);
    let n: u32 = cstr_len(p, off);
    if cur + n >= IN_CAP {
        return fail("输入缓冲没有空间放外部符号名");    // ← 这条会响 ✓
    }
```

所以输入只要逼近 2 MiB，**可用的名字池空间就只有 `IN_CAP - n` 字节** ——
`n` 越大越挤，挤过头由上面那条 `fail` 报出来（✓ 那条是对的）。

## 3. 复现：同一份 `.ll`，换汇编器

```
$ genesis  loment/build/selfhost_driver.ll /tmp/s1 && /tmp/s1 ENTRY.lomt
rc=139 (段错误), 无输出
$ clang --target=x86_64-unknown-linux-gnu -nostdlib -ffreestanding -static -fuse-ld=lld \
        -o /tmp/s3 loment/build/selfhost_driver.ll && /tmp/s3 ENTRY.lomt
rc=0, 产物 3172 B, 与参考实现一致
```

**同一份输入字节，同一份输出语义，一个崩一个不崩** —— 责任落在汇编器这一格，
与代码生成、与 `.lomt` 源都无关。这一段就是最小复现器（不需要构造语料，
现成的驱动单元加上几 KB 就够了）。

## 4. 量出来的线

| 版本 | `.ll` 字节 | 与 2 MiB = 2097152 的差 | 结果 |
|---|---|---|---|
| 桩（等长替换） | 2082032 | 低 15 KB | 定点 4/4 ✓ |
| **扁平（现役）** | **2095761** | **低 1377 B** | 定点 4/4 ✓ |
| 嵌套 A1（去掉长字符串） | 2099742 | 高 2.6 KB | 段错误 ✗ |
| 嵌套 B（连调用点都删） | 2099612 | 高 2.5 KB | 段错误 ✗ |
| 嵌套（原版） | 2100891 | 高 3.7 KB | 段错误 ✗ |

**现役这一份只剩 1377 B 余量。** 也就是说这不是"很远的容量"，是**下一次改动就撞**的东西。

## 5. 已经落地的 / 还开着的

**落了地的**：一条**预算判据**（`loment_genesis_test::test_seed_fits_lomelf_input_buffer`）
—— 从 `lomelf.lomt` 里**读** `IN_CAP`（不另抄一份，与 `test_m85_codegen_table_capacity`
同一条纪律），断言种子 `.ll` 装得下，并把余量**打出来**：

```
种子 2095761 B / lomelf 输入上限 2097152 B, 余量 1377 B
```

它能在**不需要 clang、不需要 WSL** 的机器上跑（纯静态），所以这条线从此是看得见的。
**但它只报数，不抬上限** —— 越界仍然是静默的。

**1. 越界要响 —— 已落地（2026-09-18，本轮）**

`loment/tools/lomelf.lomt` 在读完输入之后加了一条守卫：

```rust
if n >= IN_CAP as u64 {
    return fail("lomelf: 输入 .ll 超过 2 MiB 上限 (输入缓冲装不下; 见 docs/192)");
}
```

与 `copy_name` 那条、与 `driver.lomt` 里 `MAX_USE` / `MAX_ADDIN` 的注解
（"超限**报错退出**, 绝不静默丢"）是同一条纪律。判据是
`loment_elf_test::test_lomelf_selfhost_reports_oversized_input`：拿仓库里最大的那份 `.ll`
（种子）+ 注释填充撑过 2 MiB 喂给自举镜像，要求**非零退出**、**stderr 指出是 2 MiB 上限**。
它与上面那条 `test_lomelf_reports_unsupported_instead_of_miscompiling` 同一个家族 ——
**不是"能不能编"，是"编不出来时说不说"**。

因为动的是 genesis 的源，`loment/build/genesis/`（二进制 + SHA256SUMS）跟着重生成了一笔
机械提交；`loment_elf_test` 里"lomelf(种子) → 编译器 → 自编译产物 == 种子"那两条
仍然全过 —— 说明新的 genesis 照样能把种子汇编出来（种子 2095775 B，仍在上限之内）。

**2. 抬上限**（还开着，大）：`IN_CAP` 是**布局算出来的**，不是随手定的 ——
`M_IN = 8192` 起、`M_TXT = 2105344` 接，`IN_CAP` 正好是两者之差；后面
`M_OUT` / `M_GB` / `M_TAB` / `M_OBJ` 与 `ARENA`（13 MiB）都跟着它排。
抬一格要连**整条布局**和 PE 垫片那边的预算一起复核，是独立的一件事。
**做了 1 之后它从"防段错误"降级成"能不能编更大的单元"** —— 是容量问题，不是正确性问题。

**3. ⚠ 一个没有判据兜底的缺口：改了 `lomelf.lomt` 却忘了 `--emit`，门禁照样绿**（还开着，小）

`loment_genesis.check()` 验的是 **genesis 与它自己的 `SHA256SUMS`** 一致（那份 SUM 是
`--emit` 一起写的）+ bootstrap.sh 引用了它。所以"改了源、没重生成"时**哈希与新二进制
一起没动**，那条判据报告的是"一致"—— 发布出去的却是一个**陈旧的汇编器**。
这与"种子忘了重生成"是同一个形状，而种子那边**有**判据（`loment_seed_test` 的
"种子 == 参考实现的产物"）—— genesis 这边没有对应的一条。

**可行的形状**（试过别的路，记下来省得再走）：**不能**拿字节比"重生成的 genesis == 提交的
genesis" —— genesis 是 **clang** 的产物，clang 一升级就全红，那是台假红机。
能比的是 **IR**：`lomelf.lomt → IR` 那一步走的是**种子**（确定的，与 clang 无关），
所以把那份 IR 的哈希也固化下来（`emit` 时一起写，`check` 时重算一遍比），
就能把"源变了、产物没跟上"变成一条**确定**的红。参种子那边那条的同构做法。

**顺序**：1 已做（把静默错编变成报错退出）；2 是容量；3 是防漂 —— 三件互相独立。

## 6. 两条教训

1. **比"大小"之前先问清是哪个东西的大小。** 这一轮的错判全在**比错了对象**：
   我比的是**源文件**长度（2791 B 对 2791 B，看起来"等长 ⇒ 不是长度问题"），
   而决定这件事的量是**产物 `.ll`** —— 同一份源，两版差 **18 KB**。
   `--emit` 的输出字节数一直在手边，我却拿了个更容易量的代理量去下结论。
2. **"换一坨等长的东西就好了"不是因果证据**，只要那个替换顺带改了别的量。
   能把责任分清的实验长这样：**固定输入，换一个变量**（同一份 `.ll`：genesis vs clang）。

## 7. 与另一侧的不对称（记着，别去找不存在的对称）

`tools/lomelf.py`（Python 孪生，参考侧）**没有这个上限**：它 `read_bytes` / `read_text`
整个读进来，能装更大的 `.ll`。所以这一格的不对称是**能力差**，不是实现差 ——
自举镜像受限于一张固定内存图，参考侧不受限。

⇒ 修法 1 只在**自举镜像**上加一条拒绝，参考侧仍会照编。这与
`docs/188` §7.2 那条"参考实现收、自举侧拒"是同一类**诚实的分歧**：
拒的话里要写清是**谁的上限**、上限是多少，别让用户以为是自己的 `.ll` 有问题。
