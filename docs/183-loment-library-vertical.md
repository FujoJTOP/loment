## 0. 一句话

**卖点是在"第一眼"立的，而它在"运行"这一刻塌。** 这条垂直的目标只有一个：
**让 README 上敢写的那句话，照着做能跑通。**

判断标准因此是可证伪的 —— 不是"某层做完了"，而是**照着 README 的说法做一遍，`loment run` 出正确结果**。

## 1. 卖点矩阵：原话 / 今天 / 卡在哪一行

| README 上敢写的话 | 今天真不真 | 卡在哪 |
|---|---|---|
| `README.md:12`「**calls libraries written in other languages — ten of them, end to end**」 | 4 个语言（C/C++/Rust/Zig）**只吃自包含的 freestanding 对象**；另 6 个**只是把字符串递给解释器**，**调不了它的 API** | `lomelf.py:2413-2419`（未定义符号**硬拒**）· `proc.lomt:18-19`（只在 Linux/ELF） |
| `README.md:14`「**reads source written in other languages' syntax — C, Rust, Go, Java, Python**」 | 只读**声明**，不读实现 | `potato.py:29-32`：v0/v1/v2 三版顶层字段里**没有 `body`** —— 且 `docs/179:70` 明说这是**结构性扩展**，不是加个字段 |
| 「外部库」在**库系统**里的位置 | **不存在** | `lpi_cli.lomt:1176`（拒非 Loment 库）· `lomelf.py` 全文搜 `deps` **零命中** |
| 语料 15 个项目里真能调的 | **44 条，全部来自 Rust**；Python / Java **归零** | `lomt_from.py:80-87` `_ffi_ok`：只收标量 + `ptr` |

**"表层"的准确定义**：不是某一层薄，而是**两条断开的半截**。

- `--link` 要你**手工挑好**一个自包含的玩具对象喂进去；
- `lompi` 只认 Loment 源码库，`install` 对别的直接拒（`lpi_cli.lomt:1176`）；
- 两者**只在源码里那个符号名上相接**，此外零代码关联。

中间那一段 —— **"这个库在哪、什么形态、怎么取、怎么装、怎么声明"** —— **不存在**。
而语法层产出的东西**恰好就是 FFI 声明**（`lomt_from.py:11-16`），也就是说它今天唯一的
用处是"给外部实现抄一份接口"。

## 2. 目标（2026-09-17 用户定）

| 维度 | 决定 |
|---|---|
| **靶子** | **三个都要**：一个真实 **C 库**（zlib/lua/sqlite）· 一个 **Python 库**（numpy/requests）· 一个 **Rust crate** |
| **二进制侧** | **三条都要**：静态 libc · 动态库装载（阶段 3）· 运行期嵌入（阶段 4） |
| **解禁方式** | **二进制禁令解除，但用 `choose` 开关** —— 用户原话：**"choose 就是 loment 最伟大的发明"** |

**"都要"指 0.1.4 的范围，不指并行开工。** 三条二进制路线之间有**硬依赖**（阶段 4 必须以
阶段 3 打底，`docs/173:53-55`），下面是次序。

## 3. 架构：让"外部库"成为库系统的头等公民

今天"一个库 = 一个目录里的 `.lomt`"（`docs/168:8`）。这条垂直要把这句话**推广**成：

> **一个库 = 一份声明面 + 一份实现（源码**或**二进制）+ 一个身份。**

| 件 | Loment 库（今天） | 外部库（要做的） |
|---|---|---|
| **声明面** | 就是 `.lomt` 本身 | **由语法层生成**的接口单元（`docs/179` 那条链的产物） |
| **实现** | 同目录的 `.lomt` | `.a` / `.so` / `libpython` / 一个解释器 |
| **身份** | Merkle 内容哈希（`docs/168:29`） | 推广：源码哈希 ⊕ 二进制哈希 —— **二进制也要进身份**，否则"同一份声明绑到不同的机器码"正是 `docs/168` 要防的那种错合并 |
| **发现** | `deps/` → store → 四根（`lomentc.py:2116-2130`） | 同一条 `use <名字>`，只是在 `deps/<名字>/` 里多认一个**接口单元 + 二进制** |
| **取/锁** | `lompi`（registry = 同布局的 git 仓） | `lompi` 多认一种成员 |

**关键点：`use <名字>` 是唯一需要动的地方。** 只要 `deps/<名字>/` 里能同时存在
`<名字>.lomt`（声明面）与二进制，编译器就**不需要知道**它是外部的 —— 它照旧 `use`，
只是那些 `extern fn` 这次**真有人提供**。

### 3.1 `choose` 开关：把"禁令"从**全局**改成**每程序**

`docs/168:152-159` 把"二进制分发"列进**不做**。用户 2026-09-17 定的解禁方式不是删掉这条，
而是**把它变成一个 `choose` 开关**：

- **默认仍然是禁的**（不写 `choose` 就是今天的行为）—— 那条纯度主张**原封不动**；
- 写 `choose <二进制开关>` 的程序才允许把二进制依赖链进来。

这与 `docs/182` 的设计严丝合缝：**官方开关是核心语法的硬写法**（用户原话："未来官方写入的
choose 也是硬写法"），所以它是**核心语法**的一个新开关名，不是 `set choose` 那种用户自定义开关。

**收益**：可审计（`choose` 在根单元、只许一次、库不许写）、可逐程序关闭、
而且 `no_std` 与它在同一套机制里。

## 4. 分阶段（每步独立可交付 + 可证伪）

判据的形式统一为：**照着 README 的说法做一遍，`loment run` 出正确结果**。
每步都要有**两侧**（参考实现 + 自举）—— `docs/158` §5 那条。

| # | 阶段 | 解开什么 | 证伪判据（端到端） |
|---|---|---|---|
| **V0** | **结构**：外部库在库系统里有位置 | `deps/<名字>/` 能放"接口单元 + 二进制"；`lompi` 能取/锁/校验它 | 一个**手工搭的**外部库目录，`use <名字>` 能解析、能链、能跑。**后端仍是玩具**（自包含 freestanding），所以这一步不动链接器 |
| **V1** | **静态 libc** | 带 libc 依赖的**真实 C 库** | `loment run` 调 **zlib** 的 `compress`/`uncompress`，解压回原文。zlib 是 `.a` + 依赖 `malloc/free/memcpy` |
| **V2** | **动态库装载**（`docs/173` 阶段 3） | "装好的 `.so`" | `loment run` 调**系统装的** `libz.so`（不静态链），自己解 `PT_DYNAMIC` + 重定位 |
| **V3** | **运行期嵌入**（阶段 4） | Python / Java **的 API** | `loment run` 调 **`numpy`** 算一个数组的和。要 `libpython` + CPython C-API 胶水 |
| **V4** | **语法层解真实源** | 从**真实库**生成声明面 | 喂 **`zlib.h`**（typedef / 函数式宏 / `unsigned long` / `Bytef*`）→ 接口单元 → V1 那条跑通。今天 C 前端是**轻量正则**，`zlib.h` 会当场碎 |
| **V5** | **`choose` 解禁开关** | 二进制从**全局禁**变成**每程序可开** | `choose <开关>` 的程序能链二进制；**不写就编译不过**（且报错说清为什么） |

**次序的理由**：V0 是"接成一条"（用户那条垂直的本体）；V1 是**最小的真实库**（C 已是
最强的那条腿）；V2/V3 是 `docs/173` 的阶段 3/4；V4 让 V1–V3 的声明面**不必手写**；
V5 是纪律面，放在最后是因为它要等"二进制真的能用"才有意义。

## 5. 代价与风险（如实记，不粉饰）

1. **V3 是另一个量级。** CPython C-API 的胶水（引用计数、GIL、`PyObject*` 的生命周期）
   不是"再写个加载器"。`docs/173:53-55` 已经把它单独列为阶段 4。
2. **PE 侧全线缺失。** `--link` 配 `--target pe` **明确拒绝**（`lomelf.py:2472-2474`），
   动态库在 PE 上要**自己解导入表**。这条垂直在 Linux/ELF 上能走通时，Windows 可能还在原地。
3. **两个实现的差距会被真实库放大。** `docs/158` §4 里 #8（括号 `ptr` 表达式 `as` 整数，
   自举发 `zext i32` **截地址**）、#9（自举链接器 **4 MiB** 暂存上限）、#10（PC64 符号扩展）
   —— 玩具对象撞不到，真库会。
4. **与 `docs/176` 直接冲突。** 这条垂直会**持续动冻结面**（语法层、`extern` 签名、`choose`、
   链接器符号约定），而 `docs/176` 测出来的结论是"改冻结面贵在**架构差**不是行数"。
   每一次改动都要走 `docs/158` §5 四条 + 两个实现同一次提交。**这是本计划最大的成本项。**
5. **Rust crate 靶子可能撞死。** `_check_representable` **直接拒** `generics`/`instances`
   （`lomt_from.py:55-61`），而 crates.io 上的公开 API 几乎全是泛型。
   所以要**提前选好**：靶子必须是那些**有 `#[no_mangle] extern "C"` 面**的 crate
   （`*-sys` 那一类，如 `zstd-sys`/`lz4-sys`），否则这条靶子在 V0 就过不去。
6. **"全部同时"不是并行开工。** 三条二进制路线有硬依赖；V3 之前 V2 必须站稳。

## 6. 不做什么（这条垂直的边界）

- **不做"从声明自动生成绑定"** —— 用户 2026-09-16 已经定过：**"兼容" = 直接调用外部库**
  （`docs/173:3-7`）。
- **不把 FFI 构建交回 clang/lld** —— 同一条：**"全部自己做"**。
- **不做注册中心服务端**（`docs/168:152`）。
- **不新增语法去做"依赖声明"** —— 依赖永远是源码里的 `use`（`docs/168:38-40`）。
  这条垂直要新增的语法只有 **`choose` 的一个官方开关**。
