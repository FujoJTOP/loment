# 240 · 零宽阶段：**一帧，没有载荷**（`docs/218` §11 那条静态规则）

> 状态：**已落地**（2026-10-13）。`docs/218` §11 说宽度从 0 起、而"宽度 0 ≠ 拒绝"——
> 它是**只够验证对端字节**的那一点流量。§11 自己写了怎么证伪这一轮：
>
> > 如果"零宽流量"最后能被用来传任意字节（比如把载荷塞进形式对象的字段里），
> > 那它就是**换了名字的清单**，这一轮作废。判据形态：零宽阶段能发什么，必须由一条
> > **静态规则**钉死（"只允许产物字节与它的证明"），而不是靠约定俗成。
>
> 这一篇就是那条规则，**能跑的那种**。
>
> 一句话：**零宽阶段只有一帧；那帧定长，而且没有一处能放载荷。**

## 1. 规则

```
LZW0 | kind(1) | reserved(3，必须全 0) | hash32 | digest32        = 72 字节
```

* **`kind` 只有两个**：`1` = 陈述（那份产物 / 它的形式对象），`2` = 证明（对它的一枚摘要）。
  **多一个种类就是多一条通道**，所以种类表是封闭的。
* **两个 32 字节都是定长摘要**，不是能伸缩的不透明块 —— 一个能伸缩的字段就是一条载荷通道。
* **没有长度字段，也没有载荷字段**。这条是最要紧的：**"多塞点东西"在形状上就落不下去。**

## 2. §11 的证伪，落在两条判据上

| 想把载荷塞进去的路 | 结果 |
|---|---|
| 真帧后面挂字节（哪怕一个） | `bad-length` —— **多一个字节也是长度不对** |
| 塞进保留位 | `reserved-nonzero` —— 保留位必须全 0 |
| 改魔数 / 用没登记的种类 | `bad-magic` / `bad-kind` |
| 截断到 71 字节 | `bad-length` |

两条实现（`tools/loment_zwframe.py` ↔ `loment/tools/lomzwframe.lomt`）在这些结论上
**逐字节相同**；判据 `tools/loment_zwframe_test.py` 同时钉住"两边一样"**和**"结论本身对"——
只比"两边一样"是不够的：两份都放行"多一个字节的帧"也会一样。

> 这里有个细节值得写下来：`parse` 那侧"十六进制本身不合法"是**一条拒绝**（`bad-hex`），
> 而 `make` 那侧同样的输入是**用例不成形**（退出码 1）。两处口径不同是**照参考实现的**：
> 那边 `bytes.fromhex` 抛异常，在 `make` 里是坏输入、在 `parse` 里是"这帧不合法"。

## 3. 与准入那个数的接缝

`docs/238` 里 `w0` 的三刻度原先是 `(0, 1, 1)` —— 那个 `1` 是**我随手写的**，而这一篇把
"只够一次验证交换"变成了一个**具体的字节数**：**72，就是一个帧长**。

所以 `w0` 的字节预算改成 `(0, 72, 1)`，而且它**不是各写一个 72**：
`loment_admit.WIDTH["w0"]` 直接取 `loment_zwframe.FRAME_LEN`，
`loment/tools/lomadmit.lomt` 的 `width_bytes(0)` 也改成了 72 —— 判据
`test_w0_byte_budget_is_exactly_one_frame` 钉住"这两个数是一个数"。
**分开写就会漂**：一边说"只够一次验证交换"、另一边说"能给 64 KiB"，而 §11 的立足点正是前者。

## 4. 路上撞出来的一个编译器缺陷（已开 issue #289）

写 `lomzwframe.lomt` 时第一版写的是

```rust
v = v * 10 + (c - 48);          // v: u64, c: u32
```

`lomentc.check` **一个字都不报**，而发出来的 IR 是

```llvm
%t23 = add i64 %t20, %t22        ; <-- i64 + i32
```

clang 当场拒（`'%t22' defined with type 'i32' but expected 'i64'`）。**检查期放行、后端拒**，
而且症状离病因很远（"clang 说 IR 不合法"，不是"这里类型不匹配"）。处理：显式 `as u64`，
并按仓里的规矩开 issue（#289，带最小复现）—— 不在这一笔里顺手改编译器。

（与 #265 那件不是一回事：#265 是自举侧**无声地死**，这一件是参考实现**发出坏的 IR**。）

## 6. 写明的边界

* **这一篇不是零宽阶段的实现**：它规定的是**那一帧长什么样、能装什么**，不是"什么时候发、
  发给谁、怎么与 `qual_feed` 记第一笔 hit"。那是 `docs/218` §11 后半段与台账那一侧的事。
* **它没有把 `w0` 变成一条能拦人的规则**。判据能拒一帧不合形的字节，但**拦不住**一个
  程序绕过这套工具自己去发字节 —— `docs/218` §12 那条前提没变（执行者本身可改）。
  这一篇给的是"**合规的零宽流量长什么样**"，以及"**它装不下载荷**"。
* **帧的布局还没有进 L0**。它是跨两端要一致的东西，所以它的天然归属是契约的 `formats`
  段（`lom/fuai.lom` 里那条 `shm_frame_v2` 的位置）—— 但那是一次契约变更，要过 `lom/`
  那道门（admin）与跨线流程。**先有能跑、能证伪的规则（这一篇），再谈把它写进契约。**
